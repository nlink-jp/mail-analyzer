## 設計思想

mail-analyzer は 3 つの中心的な原則に従う:

1. **多層防御**: ルールベースのインジケーターは既知のパターンを偽陰性ゼロで捕らえ、LLM は
   ルールが取りこぼす未知のパターンを捕らえる。どちらの層も単独では十分でない。

2. **まず決定的に、次に確率的に**: インジケーターは再現可能で説明可能な結果を出す。LLM は
   ニュアンスを加えるが、その出力は必ず検証され制約される。

3. **解析は fail open、分類は fail closed**: パースは成功したが LLM が失敗した場合、ツールは
   それでもインジケーターの結果を出力する。パースが失敗した場合、ツールはエラーで終了する
   （部分的な結果は出さない）。

## 解析パイプライン

```
入力 (.eml / .msg)
    │
    ▼
┌────────────────┐
│ パーサー       │  ファイルの SHA-256 ハッシュ
│                │  ヘッダー抽出 (Subject, From, To, Return-Path,
│                │    Reply-To, Authentication-Results, Received, X-Mailer)
│                │  本文抽出 (text/plain, text/html, 文字コード変換)
│                │  添付抽出 (メタデータ + 添付ごとの SHA-256 ハッシュ)
└──────┬─────────┘
       │
       ▼
┌────────────────┐
│ インジケーター │  ルールベース、決定的
│                │
│  auth.go       │  SPF / DKIM / DMARC の判定結果のパース
│  sender.go     │  From↔Return-Path、表示名のなりすまし、Reply-To
│  url.go        │  URL 抽出、defang、分類
│  attachment.go │  拡張子のリスク、マクロ検出、二重拡張子
│  routing.go    │  X-Mailer の分類、Received ヘッダーの解析
└──────┬─────────┘
       │
       ▼
┌────────────────┐
│ LLM            │  Gemini (Vertex AI) による本文解析
│                │  nonce タグ付きのプロンプトインジェクション対策
│                │  構造化 JSON 出力 (response_mime_type)
│                │  指数バックオフ + ジッターによるリトライ
└──────┬─────────┘
       │
       ▼
┌────────────────┐
│ 総合判定       │  インジケーター + LLM をマージ → 最終判定
│                │  is_suspicious, category, confidence, reasons, tags
└────────────────┘
       │
       ▼
    stdout (JSON)
```

## パーサーの設計

### なぜ内部パーサーなのか（外部ツールではなく）

初代の mail-analyzer は外部 CLI ツールとして `eml-to-jsonl` と `msg-to-jsonl` に依存していた。
これは配布の複雑さとバージョンの結合を生んだ。v2 は次の理由からパーサーを内部化した:

- **単一バイナリでの配布**: 実行時に外部依存が無い
- **添付のバイナリへのアクセス**: 外部ツールはメタデータしか出力しないが、SHA-256 ハッシュを
  計算するには生のバイトが必要である
- **ヘッダーへのアクセス**: Return-Path、Reply-To、Authentication-Results、X-Mailer が必要で、
  外部ツールはこれらを露出していなかった

### 文字コードの扱い

電子メールはレガシーな文字エンコーディングの最後の砦の 1 つである。日本語のメールは
ISO-2022-JP、Shift_JIS、EUC-JP を頻繁に使う。パーサーは文字コード変換に
`golang.org/x/text/encoding/htmlindex` を用い、IANA に登録されたすべての文字コードをカバーする。

### RFC 2047 の壊れた encoded-word の修復

一部の MUA（メールユーザーエージェント）と MTA は、ヘッダーの折り返しの際に RFC 2047 の
encoded-word の内部に改行を挿入し、Base64 のペイロードを空白で分断する。標準の
`mime.WordDecoder` はこれに出会うと、（エラーを返さずに）黙って入力をそのまま返す。本パーサーは
出力にデコードされていない `=?..?=` のマーカーがあることを検出し、Base64 ペイロードから空白を
取り除いて再試行する。

**なぜ全ヘッダーから空白をすべて取り除かないのか？** それでは表示名やその他のヘッダー
フィールドの正当な空白が壊れてしまう。

## インジケーターエンジン

各インジケーターモジュールは決定的で、説明可能な結果を出す。インジケーターは **strong** な
シグナルと **weak** なシグナルに分類される。

### 認証 (auth.go)

`Authentication-Results` ヘッダーを SPF、DKIM、DMARC の判定結果についてパースする。

**なぜ weak シグナルなのか？** SPF と DMARC は、転送（Gmail → 別のアカウント）、メーリング
リストのリレー、サードパーティのマーケティングプラットフォーム（Salesforce Marketing Cloud、
SendGrid）のために、正当なメールでも頻繁に失敗する。E2E テストでは、正当な SUBARU の
ニュースレターが、転送されていたために SPF と DMARC の両方に失敗した。SPF/DMARC の失敗だけで
フラグを立てると、許容できない偽陽性率になる。

**決定**: SPF/DMARC の失敗は weak シグナルとする — 少なくとも 1 つの strong シグナルと
組み合わさったときにのみ判定に寄与する。

### 送信者の整合性 (sender.go)

| Check | Signal | Rationale |
|-------|:---:|------|
| From ↔ Return-Path のドメイン不一致 | Strong | フィッシングメールはほぼ必ず異なる Return-Path ドメインを使う |
| 表示名がメールアドレスを含む | Strong | 攻撃者は受信者を騙すために表示名に偽のメールアドレスを埋め込む |
| Reply-To のドメインの乖離 | Strong | 返信を攻撃者の管理するアドレスへ向ける |

**サブドメインのマッチング**: `bounce.mag.subaru.jp` は `mag.subaru.jp` と関連するものとみなす。
正当な送信者はバウンス処理にサブドメインを使うことが多く、これらにフラグを立てると偽陽性を生む。

**なぜ登録可能ドメイン（eTLD+1）を見ないのか？** public suffix list への依存が必要になる。
サブドメインのサフィックスマッチングは、その複雑さなしに最も一般的なケースをカバーする。

### URL 解析 (url.go)

URL は `href` 属性とテキスト本文の両方から抽出され、重複を除いて分類される:

| Pattern | Signal | Examples |
|---------|:---:|---------|
| 無料ホスティング／クラウドストレージのサフィックス | Strong | `*.web.core.windows.net`（Azure Blob）、`*.netlify.app`、`*.herokuapp.com` |
| URL 短縮サービスのドメイン | Strong | `bit.ly`、`t.co`、`tinyurl.com` |
| 不審な TLD | Strong | `.cfd`、`.top`、`.xyz`、`.click`、`.buzz` |
| URL が `@` を含む | Strong | `https://legitimate.com@evil.com/...` |

**なぜクラウドストレージはサフィックスマッチングなのか？** フィッシングキャンペーンは Azure
Blob Storage（`*.web.core.windows.net`）や類似のサービスを大いに悪用する。信頼されて見える
ドメインで無料の HTTPS ホスティングを提供するからである。E2E テストでは、この検査が無ければ
取りこぼしていたフィッシングメール 3 通が、このパターンを使っていたことを確認した。

**なぜ不審な TLD なのか？** フィッシングキャンペーンの分析から、`.cfd`、`.top` などの安価な
TLD がフィッシングのドメインに不釣り合いに多く使われていることが分かっている。これらの TLD は
登録の要件が最小限で、費用も非常に低い。

**スキーマ URL のフィルタ**: XML の名前空間 URI（例: `schemas.microsoft.com`、`www.w3.org`）は
HTML メールに現れるが、クリックできるものではない。ノイズを避けるため、解析の前に除外する。

### 添付ファイルのリスク (attachment.go)

| Pattern | Signal | Examples |
|---------|:---:|---------|
| 危険なファイル拡張子 | Strong | `.exe`、`.scr`、`.bat`、`.vbs`、`.ps1`、`.iso`、`.lnk` |
| マクロ有効の Office | Strong | `.xlsm`、`.docm`、`.pptm` |
| 二重拡張子 | Strong | `invoice.pdf.exe` |

**なぜ内容を検査しないのか？** このアナライザーが処理するのはメールのメタデータと構造であり、
バイナリのペイロードではない。内容の検査（サンドボックス、AV スキャン）は別のツールの責務で
ある。脅威インテリジェンスのフィードと突き合わせるために SHA-256 ハッシュを提供する。

### 経路の解析 (routing.go)

**X-Mailer の分類**: X-Mailer ヘッダーにある既知の大量配信ツール（PHPMailer、SwiftMailer
など）にフラグを立てる。これらのツール自体が悪性なのではないが、フィッシングキャンペーンで
よく使われる。

**Received ヘッダーの解析**: localhost／unknown な発信元、ローカルのドメイン名（`.local`、
`.localdomain`）、逆引き DNS の無い IP のみの HELO を検査する。これらのパターンは、侵害された
ホストや設定の不十分なインフラを示す。

**注意**: ExactTarget／Salesforce Marketing Cloud のようなマーケティングプラットフォームは、
内部の経路に `.local` ドメインを使う。これは strong シグナルではなく weak シグナル
（参考情報）としてフラグを立てる。

## LLM 解析

### なぜ Vertex AI 経由の Gemini なのか？

- **構造化出力**: `ResponseMIMEType: application/json` がモデルを妥当な JSON の生成に制約し、
  パースの失敗を無くす
- **ADC 認証**: API キーの管理が不要。GCP 上ではサービスアカウント、ローカルでは
  `gcloud auth` を使う
- **組織のツールとの一貫性**: 他のツール（mail-triage、news-collector、ai-ir2）が同じ SDK を
  使っている

### なぜ google.golang.org/genai なのか（cloud.google.com/go/vertexai/genai ではなく）？

`vertexai/genai` SDK は 2025 年 6 月に非推奨となり、2026 年 6 月に削除が予定されている。
`google.golang.org/genai` SDK が推奨される後継であり、同じ API を提供しつつ活発に保守されて
いる。

### プロンプトインジェクション対策

メールの内容は信頼できず、LLM の解析を上書きするために作られた敵対的な指示を含みうる。対策は
多層である:

1. **プロンプト先頭の防御指示**: システムプロンプトはインジェクション対策の規則から始まる。
   LLM はコンテキストの冒頭にある指示により注意を払う。長い解析規則の後にこれを置くと、優先度が
   下げられる危険がある。

2. **nonce タグ付きの XML 境界**: メールのデータは
   `<user-data-{random_hex}>...</user-data-{random_hex}>` で包む。ランダムな nonce は、攻撃者が
   閉じタグをあらかじめ仕込むことを防ぐ。

3. **構造化出力の制約**: `ResponseMIMEType: application/json` が JSON 出力を強制し、自由形式の
   指示追従を難しくする。

4. **出力の検証**: カテゴリの値はホワイトリストと照合し、未知の値は既定で `safe` とする。
   confidence は [0, 1] にクランプする。tags と reasons は 5 件で打ち切る。

### リトライ戦略

API のエラー（429、500、503）は指数バックオフ（基準 5s、上限 120s）に ±1s のジッターを加えて
リトライする。パースのエラー（LLM からの不正な JSON）はリトライしない — 一時的な失敗ではなく、
プロンプトかモデルの問題を示すからである。

## 総合判定

### オンラインモード（LLM あり）

まずインジケーターを計算し、事前計算された構造化シグナルとして LLM に渡す。LLM は
インジケーターとメールの内容の両方を見て、その双方を統合した判定を出す。

**なぜインジケーターを LLM に渡すのか？** インジケーターが無ければ、LLM は SPF/DKIM/DMARC、
送信者の整合性、URL のリスクなどを独立に評価しなければならない。これは労力の重複であり、
一貫性の欠如を招く。事前計算したインジケーターを与えることで、LLM は内容の解析と文脈的な判断に
集中できる。

### オフラインモード（LLM なし）

`--offline` を指定すると、ルールベースのインジケーターだけを使う。総合判定は strong/weak
シグナルのモデルに従う:

- **strong シグナル**（送信者の不一致、不審な URL、危険な添付、不審な X-Mailer）: それぞれ
  単独でフラグを立てるに足る
- **weak シグナル**（SPF 失敗、DMARC 失敗、不審な経路のホップ）: strong シグナルと
  組み合わさったときにのみ数える

**なぜこの切り分けなのか？** 実際のフィッシングのサンプルを用いた E2E テストで、SPF/DMARC の
失敗だけでは、正当な転送メール（SUBARU のニュースレター）に偽陽性を出すことが分かった。
少なくとも 1 つの strong シグナルを要求することで、この種類の偽陽性を無くしつつ、本物の
フィッシング（必ず複数の strong シグナルを示す）の検出は保たれる。

オフラインモードの confidence は 0.8 で上限を設ける。ルールベースの解析は内容を評価できず、
それは LLM の解析だけが埋められる限界だからである。

### カテゴリ分類

| Category | When used |
|----------|-----------|
| phishing | 資格情報の窃取、偽のログイン、ブランドのなりすまし |
| spam | 望まれていない商業メール |
| malware-delivery | 危険な添付、またはペイロードへのリンク |
| bec | ビジネスメール詐欺、請求書詐欺 |
| scam | 前払い金詐欺、宝くじ、偽造品 |
| safe | 正当なメール |

オフラインモードでは、不審なメールのカテゴリは既定で `phishing` となり、危険な添付がある場合は
`malware-delivery` となる。LLM モードはより細かい分類を行う（例: 偽造品には `scam`、請求書
詐欺には `bec`）。

## 設計判断と根拠

| Decision | Rationale |
|----------|-----------|
| Python ではなく Go | 単一バイナリ、起動が速い、eml-to-jsonl/msg-to-jsonl のパーサーをそのまま再利用できる |
| 外部 CLI ではなく内部パーサー | 単一バイナリでの配布、ハッシュ計算のための添付バイトへのアクセス、Return-Path/Reply-To/Authentication-Results へのアクセス |
| MD5/SHA-1 ではなく SHA-256 のみ | MD5 と SHA-1 には既知の衝突攻撃がある。SHA-256 は IoC の突き合わせの標準である（STIX 2.1、VirusTotal） |
| google.golang.org/genai SDK | vertexai/genai は 2025 年 6 月に非推奨。genai が現役の後継である |
| プロンプト先頭のインジェクション対策 | LLM は早い位置の指示により注意を払う。長い規則の後に対策を置くと優先度が下げられる危険がある |
| SPF/DMARC を weak シグナルとする | 実世界のテストで、転送された正当なメールが SPF/DMARC に失敗することが分かった。strong シグナルを要求することでこの種類の偽陽性が無くなる |
| 送信者比較にサブドメインマッチング | 正当なバウンス処理はサブドメインを使う。完全一致のドメイン比較は偽陽性を生む |
| 不審な TLD のリスト | 安価な TLD（.cfd、.top、.xyz）はフィッシングに不釣り合いに多く使われる。これにフラグを立てることで E2E テストでフィッシングメールをさらに 2 通捕らえた |
| 無料ホスティングのリストに Azure Blob Storage | E2E テストのフィッシングメール 12 通のうち 3 通が、資格情報を収集するページに *.web.core.windows.net を使っていた |
| オフラインモード | GCP の資格情報なしで使える。バッチ処理、CI/CD、エアギャップ環境で有用 |
| 構造化 JSON 出力 | パイプに向く。下流の処理（jq、SIEM への取り込み、脅威インテリジェンスとの突き合わせ）を可能にする |
